# Архитектура БАТЫС AI

## Контур решения

```text
 Веб / PWA (public/)          Мобильное приложение (mobile/, Expo)
          │                              │
          └──────────── HTTP JSON ───────┘
                          ▼
              Node.js 22+ · Express 5 (src/server.mjs)
                          │
     ┌────────────────────┼─────────────────────────┐
     ▼                    ▼                         ▼
 parser.mjs          analyzer.mjs              openai-review.mjs
 DOCX/PDF/XLSX/      объяснимый анализ:        опциональная проверка
 CSV/TXT → текст     подразделения, функции,   кандидатов через
                     доказательства            Responses API
                          │
                          ▼
              store.mjs → PostgreSQL 16 (Docker) или память
                          │
                          ▼
              report.mjs → печатное аналитическое заключение
```

## Как агент приходит к выводу

1. **Извлечение.** Текст документа делится на пункты с номерами (`5.5.4`, `а.`). Раздел «Структура» даёт список подразделений. Заголовки вида «Директор ДККМ:» и «Департамент X:» задают владельца для пунктов ниже.
2. **Функции.** Функцией считается пункт с управленческим глаголом («организует», «контролирует», «анализирует»…). Регулярные выражения используют Unicode-границы слов, потому что `\b` в JavaScript не распознаёт кириллицу.
3. **Нормализация.** Слова приводятся к основе простым русским стеммером: отбрасываются глагольные и именные окончания («организует» и «организуют» дают одну основу). Затем считается сходство множеств основ: 60% Жаккара и 40% вложенности.
4. **Сопоставление функций.** Используется глобальное жадное назначение один-к-одному: сначала самые сильные пары, поэтому почти идентичный пункт не «уводит» более слабое совпадение. Функция без пары с порогом ≥ 0,38 считается **потерянной**.
5. **Сопоставление подразделений.** Учитываются название и **переход функций**: `score = max(имя, 0,35·имя + 0,65·доля функций, ушедших в новое подразделение)`. Поэтому переименованный департамент распознаётся как преобразованный, а у упразднённого указывается, куда ушли его функции («2 из 3 функций перешли в ДОА»).
6. **Классификация.**
   - `function_moved`: пара найдена, владелец изменился.
   - `function_lost`: пары нет, или единственный похожий пункт принадлежит другому владельцу, у которого эта функция была и раньше. Например, ДККМ 5.5.4 в ред. 9.
   - `function_narrowed`: пара найдена, но из формулировки выпали ≥ 3 значимых слова (≥ 20%), например «ежеквартально», «по итогам года».
   - `function_duplicate` / `conflict_risk`: похожие функции у разных владельцев в новой редакции. Типовые обязанности руководителя (повторяются у ≥ 3 владельцев) и функции, относящиеся к разным подразделениям (разные аббревиатуры ДНМ/ДККМ), исключаются. Конфликт отмечается, если функция контрольная (утверждает, контролирует, согласовывает, назначает).
   - `unit_removed`: упразднён владелец функций, например должность «Директор направления внутреннего аудита». Показывается распределение его функций.
7. **Доказательства.** Каждый вывод содержит 1–2 цитаты: документ, номер пункта, владелец и фрагмент.
8. **AI-проверка (опционально).** OpenAI получает только кандидатов и цитаты, отвечает по строгой JSON-схеме и не может добавить новые выводы или источники.
9. **Эксперт.** Специалист подтверждает или отклоняет каждый вывод. Решения сохраняются и попадают в заключение.

## Почему детерминированное ядро, а не «LLM на весь документ»

- **Прослеживаемость.** ТЗ требует ссылку на пункт для каждого вывода. Алгоритм по построению не может сослаться на несуществующий фрагмент.
- **Воспроизводимость.** Одинаковые документы всегда дают одинаковый результат, и это проверяется тестами на контрольном комплекте.
- **Работа без ключа.** Основной сценарий доступен офлайн. LLM выступает вторым мнением, а не источником фактов.
- **Скорость.** Сравнение двух положений примерно по 85 тыс. символов занимает около 50 мс.

## Компоненты

| Файл | Назначение |
|---|---|
| `src/server.mjs` | REST API, загрузка файлов, демо-наборы, заключение |
| `src/parser.mjs` | Извлечение текста: mammoth (DOCX), pdf-parse (PDF), ExcelJS (XLSX) |
| `src/analyzer.mjs` | Детерминированный анализ и доказательства |
| `src/openai-review.mjs` | Проверка кандидатов через Responses API и Structured Outputs |
| `src/store.mjs` | PostgreSQL (JSONB) или память для автономного запуска |
| `src/report.mjs` | Печатное аналитическое заключение |
| `public/` | Адаптивный веб-интерфейс и PWA |
| `mobile/` | Приложение для Android и iOS на Expo (React Native) |
| `samples/` | Контрольный комплект (ред. 8 и 9) и синтетический пример |
| `test/` | Автотесты, включая проверку на контрольном комплекте |

## Масштабирование

Для промышленного контура API можно разделить на сервис загрузки, очередь заданий и worker-процессы. Файлы следует хранить в защищённом S3-совместимом хранилище. Нужно добавить корпоративный SSO, антивирусную проверку и политики хранения. Вместо стеммера можно подключить морфологический анализатор (pymorphy/Stanza) или эмбеддинги, не меняя формат выводов.
